Guides for the MLPerf Storage (MLCommons) benchmark using DLIO: installation, CLI, NFS recommendations, training, checkpointing, vectorDB, datasize examples, and NFS operation observations.


[[dliomlcommons]]
== DLIO / MLCommons (MLPerf Storage)

We will be using the MLPerf Storage benchmark from MLCommons, which leverages DLIO (from Argonne National Labs) to emulate AI training I/O without requiring GPUs.

* Source repository: https://github.com/mlcommons/storage
* Benchmark overview: https://mlcommons.org/benchmarks/storage/
* Quick start: https://github.com/mlcommons/storage/blob/main/docs/QUICK_START.md

*Note:* Installation and configuration steps in the upstream README are validated against *Ubuntu 24.04* with *Python 3.12.3*. RHEL 9.x may work but is not the primary validated client OS.

*Note:* MLCommons updates the suite regularly (current package major.minor is *v3.0*). Their repository and rules are the single source of truth if this appendix and upstream docs diverge.


[[about-mlcommons]]
=== About MLPerf Storage

MLPerf Storage characterizes how fast a storage system can supply training (and related) data when a model is being trained or checkpointed. As of the current v3.0 tooling, the suite covers:

* Training I/O (DLIO-emulated accelerators)
* Checkpointing (Llama3 scales)
* Vector database search (Milvus / RAG-style)
* KV-cache offload (LLM inference context cache)

MLPerf Storage emulates accelerators for the training workloads with DLIO. DLIO uses standard AI frameworks (PyTorch, TensorFlow, NumPy, and so on) to load data from storage to memory at the same intensity as a given accelerator.

*This emulation means that submitters do not need to use hardware accelerators (for example, GPUs, TPUs, and other ASICs) when running MLPerf Storage training.* Upstream installs the CPU-only version of PyTorch; GPUs are not required and are not used.

Instead, the benchmark replaces training on the accelerator for a single batch of data with a `sleep()` call. The sleep interval depends on the batch size and accelerator type and has been measured on systems running the real training workload. The rest of the data ingestion pipeline (data loading, caching, checkpointing) is unchanged.

There are two main advantages to accelerator emulation:

. You can test different storage systems against different emulated accelerators (for example, NVIDIA A100, H100, or B200) by changing batch size and sleep parameters / `--accelerator-type`.
. You can put a high load on the storage system by increasing the number of emulated accelerators, without purchasing or renting a large AI compute cluster.

Submission modes in the v3.0 CLI:

* `closed` — apples-to-apples; almost no tuning allowed
* `open` — documented tuning allowed
* `whatif` — exploration only; not valid for submission (exposes additional models/parameters)

This test plan covers training, checkpointing, and vectorDB benchmarks against NetApp AFX over NFS (`file` backend). KV-cache is optional and not required for the core test plan scenarios.


[[nfs-recommendations-for-mlperf]]
=== NFS version and mount option recommendations

Mount FlexGroup (or other data) volumes from NetApp AFX on every client that participates. Prefer dedicated mount points per workload family so training, checkpoints, and vectorDB data do not share the same directory tree.

For general NFS guidance, see xref:appendix-nfs-considerations.adoc[NFS Considerations] and xref:appendix-client-tuning.adoc[Client Tuning]. Workload-specific recommendations for this test plan:

[cols="1,2,3",options="header"]
|===
| Workload | Recommended NFS version | Recommended mount options / notes
| Training (sequential read-heavy) | NFSv4.1 with pNFS and session trunking | Ubuntu 22+: `vers=4.1,tcp,hard,intr,nocto,actimeo=3600,max_connect=8,rsize=1048576,wsize=1048576`. RHEL 9.x+: use `trunkdiscovery` instead of `max_connect=8`. `nocto` and long `actimeo` suit static training datasets.
| Checkpointing (sequential write + restore reads + SETATTR) | NFSv4.1 with pNFS and session trunking | Same base as training (`vers=4.1,tcp,hard,intr,max_connect=8` or `trunkdiscovery`, `rsize=1048576,wsize=1048576`). Prefer *without* `nocto` (or use a shorter `actimeo`) so attribute updates during checkpoint write/restore are not overly stale. Ensure the checkpoint folder is on shared NFS so all hosts can read what peers wrote.
| VectorDB (random read/write + metadata) | NFSv3 *or* NFSv4.1 | NFSv3: `vers=3,tcp,hard,intr,nconnect=8,rsize=1048576,wsize=1048576` often works well for metadata-heavy / random patterns. NFSv4.1: keep trunking (`max_connect` / `trunkdiscovery`) but avoid aggressive `nocto`/`actimeo` unless you validate query correctness. Point Milvus Docker volumes at the NFS mount (see <<vectordb-on-nfs>>).
|===

*Note:* Always use `hard` mounts for benchmarks. Soft mounts can mask storage issues with application-level timeouts.


[[installation-and-setup]]
=== Installation and setup

Run these steps on *every* client host that will participate. Pick one host as the launcher; configure passwordless SSH from the launcher to all other clients. Code and data paths must be identical on every host.

. Install `uv` (required package manager used by the benchmark):

[source,console]
----
curl -LsSf https://astral.sh/uv/install.sh | sh
----

. Install the MPI runtime (required for distributed runs), for example on Ubuntu:

[source,console]
----
sudo apt install libopenmpi-dev openmpi-common
----

. Clone the repository:

[source,console]
----
git clone https://github.com/mlcommons/storage.git
cd storage
----

. Optionally run the helper setup script, then activate the environment:

[source,console]
----
./setup_env.sh
source .venv/bin/activate
----

. Verify the install:

[source,console]
----
mlpstorage --help
mlpstorage version
----

The `mlpstorage` entry point runs via `uv`, which creates/updates `.venv` and installs dependencies (including DLIO) from the project lockfile.

When the launcher runs as root, add `--allow-run-as-root` to any `datasize`, `datagen`, or `run` command that uses MPI.


[[cli-structure]]
=== CLI structure (v3.0)

General form:

[source,console]
----
mlpstorage <closed|open|whatif> <training|checkpointing|vectordb|kvcache> \
  <model|algorithm> <datasize|datagen|run|configview> [file|object] [OPTIONS]
----

* Use `file` for POSIX/NFS (and similar) backends.
* Use `object` for S3-compatible object storage (see upstream object-storage guides).
* `datasize` does not take a `file`/`object` selector.

Example CLOSED U-Net3D flow on NFS/`file`:

[source,console]
----
# 1. Size the dataset
mlpstorage closed training unet3d datasize \
  --num-accelerators 2 --accelerator-type h100 \
  --client-host-memory-in-gb 64

# 2. Generate the synthetic dataset
mlpstorage closed training unet3d datagen file \
  --num-processes 4 \
  --data-dir /mnt/afx/mlperf/unet3d/data \
  --results-dir /mnt/afx/mlperf/results

# 3. Run the benchmark
mlpstorage closed training unet3d run file \
  --num-accelerators 2 --accelerator-type h100 \
  --client-host-memory-in-gb 64 \
  --data-dir /mnt/afx/mlperf/unet3d/data \
  --results-dir /mnt/afx/mlperf/results
----

For full help: `mlpstorage --help_all` or append `--help` at any subcommand level.


[[about-checkpointing-in-mlcommons-benchmark]]
=== About checkpointing in MLPerf Storage

Checkpointing reduces lost progress when training fails. Typical I/O profile:

* Sequential writes for saving checkpoint information
* Random reads for restoring from checkpoints
* Metadata operations (mostly SETATTR)

Upstream checkpointing emulates Llama3 scales (`llama3-8b`, `llama3-70b`, `llama3-405b`, `llama3-1t`). Checkpoint sizes range from about 105 GB (8B) to about 18 TB (1T). For CLOSED runs, process counts are fixed (8 / 64 / 512 / 1024 respectively).

For shared NFS on NetApp AFX, use *default* (multi-host shared storage) mode, not *subset* (node-local storage).

Upstream reference: https://github.com/mlcommons/storage/blob/main/checkpointing/README.md[checkpointing/README.md]

[[checkpointing-on-nfs]]
==== Checkpointing on NFS — test plan steps

. Mount an AFX volume for checkpoints on all participating clients (see <<nfs-recommendations-for-mlperf>>). Example mount point: `/mnt/afx/mlperf/checkpoints`.
. From the launcher, size the workload if desired:

[source,console]
----
mlpstorage closed checkpointing llama3-8b datasize \
  --client-host-memory-in-gb 512 \
  --num-processes 8
----

. Run write-only checkpoints to NFS (`file`), then clear client page cache if required, then run read-only recovery.
+
If checkpoint size per client is less than about 3× client DRAM, clear caches between write and read so recovery reads come from storage rather than client cache:
+
[source,console]
----
# Write 10 checkpoints (no reads)
mlpstorage closed checkpointing llama3-8b run file \
  --client-host-memory-in-gb 512 \
  --num-processes 8 \
  --checkpoint-folder /mnt/afx/mlperf/checkpoints \
  --results-dir /mnt/afx/mlperf/results \
  --num-checkpoints-read=0

# On each client (requires root), drop caches when needed
echo 3 > /proc/sys/vm/drop_caches

# Read/recover the same 10 checkpoints (no writes)
mlpstorage closed checkpointing llama3-8b run file \
  --client-host-memory-in-gb 512 \
  --num-processes 8 \
  --checkpoint-folder /mnt/afx/mlperf/checkpoints \
  --results-dir /mnt/afx/mlperf/results \
  --num-checkpoints-write=0
----
+
Alternatively, a single invocation can write then read without an explicit cache clear (useful for a smoke test only):
+
[source,console]
----
mlpstorage closed checkpointing llama3-8b run file \
  --client-host-memory-in-gb 512 \
  --num-processes 8 \
  --checkpoint-folder /mnt/afx/mlperf/checkpoints \
  --results-dir /mnt/afx/mlperf/results
----

. For larger models (`llama3-70b`, `llama3-405b`, `llama3-1t`), increase `--num-processes` and `--hosts` to match CLOSED process counts, and ensure aggregate client memory and NFS capacity can hold the checkpoint footprint.
. Confirm results under `--results-dir` and that write and read phases completed against the NFS path.


[[about-vectordb-search-in-mlcommons-benchmark]]
=== About vectorDB search in MLPerf Storage

The VectorDB benchmark measures storage behavior for vector similarity search (commonly used in RAG and recommendation systems). The I/O profile is generally random reads and writes plus metadata. Upstream supports Milvus indexing algorithms such as DISKANN, HNSW, and AISAQ (plus additional algorithms in `open`/`whatif`).

For this test plan, run VectorDB with Milvus data directories on NFS (`file` backend) so AFX is under test.

Upstream reference: https://github.com/mlcommons/storage/tree/main/vdb_benchmark[vdb_benchmark]

[[vectordb-on-nfs]]
==== VectorDB on NFS — test plan steps

. Install VectorDB extras on the client that will run Milvus / `mlpstorage`:

[source,console]
----
cd storage
uv sync --extra vectordb
uv pip install -e ./vdb_benchmark
mlpstorage open vectordb --help
----

. Mount an AFX volume for VectorDB data, for example `/mnt/afx/mlperf/vdb` (see <<nfs-recommendations-for-mlperf>>).
. Configure the standalone Milvus stack to store Docker volumes on that NFS path:
+
[source,console]
----
cp vdb_benchmark/stacks/milvus/standalone/minio/.env.example \
   vdb_benchmark/stacks/milvus/standalone/minio/.env
----
+
Set `DOCKER_VOLUME_DIRECTORY=/mnt/afx/mlperf/vdb` (or your NFS mount) in the `.env` file so Milvus/MinIO/etcd volumes land on AFX.
. Start Milvus and verify health:
+
[source,console]
----
docker compose -f vdb_benchmark/stacks/milvus/standalone/minio/docker-compose.yml up -d
docker ps -a
----
+
Containers `milvus-etcd`, `milvus-minio`, and `milvus-standalone` should be healthy. Default endpoint: `127.0.0.1:19530`.
. Estimate storage for the chosen index (example: DISKANN):
+
[source,console]
----
mlpstorage open vectordb datasize \
  --vdb-index DISKANN
----
. Load vectors (`datagen`) using the `file` backend:
+
[source,console]
----
mlpstorage open vectordb datagen file \
  --vdb-index DISKANN \
  --results-dir /mnt/afx/mlperf/results
----
. Run the search benchmark:
+
[source,console]
----
mlpstorage open vectordb run file \
  --vdb-index DISKANN \
  --results-dir /mnt/afx/mlperf/results
----
. Review results under `--results-dir`. For closed-division or other indexes (`HNSW`, `AISAQ`), change the mode/`--vdb-index` accordingly. Use `mlpstorage open vectordb run --help` for current options.

*Note:* VectorDB requires Docker Compose and a healthy Milvus instance for `datagen` and `run`. `datasize` can run without Milvus.


[[about-training-in-mlcommons-benchmark]]
=== About training in MLPerf Storage

Training I/O is a primary focus for this test plan. AI/ML training is typically a heavily sequential read workload on a static dataset and requires high throughput.

In the current v3.0 CLI:

* *Closed / open:* `unet3d`, `retinanet`
* *Whatif (not submittable):* `cosmoflow`, `resnet50`, `dlrm`, `flux` (in addition to the closed models)

For this test plan, use U-Net3D (closed) plus ResNet50 and CosmoFlow via `whatif` when you want those training-ingest shapes. RetinaNet is also available for closed-division exploration.

[[about-u-net3d]]
==== About U-Net3D

The U-Net3D model simulates medical image segmentation (for example, 3D imaging). Default sample size is approximately 146 MB per file (one sample per file; NumPy / TensorFlow / PyTorch readers), defined in the U-Net3D GPU YAML configs under `configs/`.

[[about-resnet50]]
==== About ResNet50

ResNet50 is used for image classification and related computer vision tasks. Individual samples are on the order of ~100–150 KB (ImageNet-like), but the workload typically packs many samples per TFRecord file, so *on-disk files are much larger* (often on the order of ~100 MB). Do not confuse per-sample size with average file size when sizing capacity or interpreting NFS histograms.

[[about-cosmoflow]]
==== About CosmoFlow

CosmoFlow models cosmology parameter prediction from N-body simulation data. Default average sample/file size is approximately 2.8 MB (one sample per TFRecord file), defined in the CosmoFlow GPU YAML configs.

[[about-retinanet]]
==== About RetinaNet

RetinaNet is a closed/open training model in v3.0 (object detection-style ingest). Use it for closed-division runs when you want an officially submittable workload beyond U-Net3D. See upstream `training/README.md` and `docs/QUICK_START.md` for RetinaNet datagen/run examples.
