SPECstorage Solution 2020 (commonly called SPEC SFS 2020) EDA workload profiles: frontend, backend, and blended terminology; NFS operation distributions; and operation definitions.


[[about-eda-frontend-backend-and-blended-terminology]]
== About EDA frontend, backend, and blended terminology

The EDA terms used in this document for workloads (frontend, backend, blended) refer to the workloads documented in SPECstorage Solution 2020. Specifically:

* *Frontend* — large number of small files, higher metadata
* *Backend* — lower number of large files, 50/50 read/write (sequential)
* *Blended* — a mix of both frontend and backend workloads

See https://www.spec.org/storage2020/ for details.


[[spec-sfs-2020]]
== SPEC SFS 2020

We will be using the SPECstorage Solution 2020 benchmark to simulate EDA frontend, backend, and blended workloads. The test profiles use the workload profiles found in the link:https://www.spec.org/storage2020/[SPECstorage Solution 2020] documentation, as well as details on how to set up and configure the benchmark.

The official EDA workload is a blend of two component workloads:

* *EDA_FRONTEND* — metadata-intensive; many small files (frontend design flow).
* *EDA_BACKEND* — sequential read/write intensive; larger assembly files (backend design flow).

In the blended workload, the process ratio is maintained at 3 frontend processes for every 2 backend processes as load increases.

[[spec-run-types]]
=== Exploratory and publishable runs

Use exploratory runs to validate mounts, size clients, and find a useful load range. Results are not publishable when you alter workload definitions, use the SM2020 automatic-search options, or otherwise depart from the official run rules. A disclosable result must follow the current link:https://www.spec.org/storage2020/docs/runrules.pdf[SPECstorage Solution 2020 Run and Reporting Rules], including the required load points and reporting package.

The official user guide and run rules are authoritative if they differ from this test plan:

* link:https://www.spec.org/storage2020/docs/usersguide.pdf[SPECstorage Solution 2020 User's Guide]
* link:https://www.spec.org/storage2020/docs/runrules.pdf[Run and Reporting Rules]

[[spec-client-sizing]]
=== Prime client and load-generator sizing

Run `SM2020` from one Prime client. The Prime client coordinates the run and collects results; load generators issue the workload. Configure passwordless SSH from the Prime client, install the benchmark at the same path on all Linux clients, and mount the same AFX paths on every listed client.

Start with at least four modern load generators, then add clients when CPU, memory, NIC, or RPC concurrency on the clients approaches saturation before ONTAP does. Distribute `CLIENT_MOUNTPOINTS` in round-robin order across clients and volumes/LIFs so the first load points do not create an artificial hotspot.

The official rules give these approximate resources for each unit of business load:

[cols="1,1,1"]
|===
| Workload | Client RAM per load unit | Storage per load unit
| AI_IMAGE | 1.7 GiB per job | 100 GiB per job
| EDA_BLENDED | 520 MiB per job | 11 GiB per job
| GENOMICS | 416 MiB per job | 3.5 GiB per job
| SWBUILD | 650 MiB per build | 5 GiB per build
| VDA | 100 MiB per stream | 24 GiB per stream
|===

Keep client CPU below sustained saturation and leave RAM for the operating system, NFS cache, and benchmark processes. If one client reaches its NIC limit, add load generators rather than only increasing load on that host.

Each `LOAD` unit is one concurrent business-metric job (for EDA, one JOB). SM2020 assigns jobs in order from `CLIENT_MOUNTPOINTS`. Jobs per client equal how often that client appears in the list, plus wrap-around after the list is exhausted. EDA_BLENDED keeps 3 frontend processes for every 2 backend processes as those jobs scale.

[[spec-installation-and-preflight]]
=== Installation and preflight

. Install Python 3.8.2 or later and PyYAML on the Prime client.
. Install the benchmark using its supplied manager:
+
[source,console]
----
python3 SM2020 --install-dir=[INSTALL_PATH]
----
. Confirm that every client can access the benchmark path and its assigned NFS mount without a password prompt.
. Verify the test directories are writable and have enough capacity/inodes for the highest planned load.
. Apply the client and ONTAP baseline from xref:benchmark-configuration-reference.adoc[Benchmark Configuration Reference], then record protocol, mount options, client count, and software versions.

[[spec-sfs-rc-example]]
=== Minimal `sfs_rc` example

Copy the supplied `sfs_rc` and change only the site-specific values. For an exploratory EDA run:

[source,config]
----
BENCHMARK=EDA_BLENDED
LOAD=1
INCR_LOAD=1
NUM_RUNS=10
CLIENT_MOUNTPOINTS=client01:/mnt/afx/eda1 client02:/mnt/afx/eda2 client03:/mnt/afx/eda3 client04:/mnt/afx/eda4
----

Use the exact workload name supported by the installed release. For a publishable run, use at least ten uniformly spaced load points and follow all current run-rule requirements. `LOAD` may also be an explicit increasing list for exploratory sweeps.

Run from the Prime client and use a unique suffix:

[source,console]
----
python3 SM2020 -r sfs_rc -s eda_baseline_256k
----

[[spec-concurrency-method]]
=== Concurrency and jobs per run

Start with 1 job per client, then increase jobs per client and client count independently. Do not begin a first-pass lab run with more than 1–2 jobs on a single load generator.

[cols="1,2,2"]
|===
| Phase | Jobs / `LOAD` | Purpose
| Smoke | `LOAD=1` (one job on the first `CLIENT_MOUNTPOINTS` entry) | Confirm SSH, mounts, free space, and result files
| Baseline | `LOAD` = number of load generators (1 job per client) | Establish a comparable starting point
| Jobs-per-client ramp | 2, 4, then 8 jobs per client (`LOAD` = clients × jobs per client) | Find per-client concurrency before adding hardware
| Client ramp | Keep jobs per client fixed; add load generators | Continue scaling after a client CPU, RAM, or NIC saturates
| Exploratory curve | Even `LOAD` / `INCR_LOAD` steps; 3–5 points is enough | Map the useful range; repeat the last useful point three times
| Publishable curve | At least 10 uniformly spaced points | Follow the current SPEC run rules; `NUM_RUNS` here is load points, not repeats
|===

Recommended first `sfs_rc` values with four load generators:

[source,config]
----
LOAD=4
INCR_LOAD=4
NUM_RUNS=5
----

That starts at 1 job per client and steps to 8, 12, 16, and 20 concurrent jobs. After a client saturates, add generators instead of raising jobs per client further. List each client once in `CLIENT_MOUNTPOINTS` for the 1-job-per-client start; repeating a client on extra mount paths is how you place a second job on that host.

. Run the smoke test (`LOAD=1`) before any ramp.
. Monitor client CPU/RAM/NIC utilization and ONTAP throughput, IOPS, latency, and protocol counters at every point.
. Stop increasing jobs when aggregate throughput no longer scales, response time rises materially, clients saturate, or capacity/inode limits approach the planned guardrail.
. Change one variable per comparison: protocol, transfer size, trunking/nconnect, client count, or ONTAP feature.

Use NFSv3 for metadata-heavy EDA frontend exploration and compare NFSv4.1 with pNFS/session trunking for backend throughput. Treat protocol comparisons as separate result sets and retain all `sfs_rc`, logs, summaries, mount output, and ONTAP samples.

[[spec-application-block-sizes]]
=== Application block sizes

SPEC SFS does not use a single `bs`. Each workload issues a mix of transfer sizes defined in `storage2020.yml` (from hundreds of bytes through 256K/512K). The storage array still sees those requests through the NFS mount: anything larger than `rsize`/`wsize` is split. Keep the mount at 256K or 1MB so backend sequential I/O is not fragmented into 64K RPCs unless that is the comparison you intend.

How the EDA profiles relate to application I/O:

* *EDA_FRONTEND* — many small files and metadata (stat/access/create). Data transfers are often small to mid-size; IOPS and RPC rate matter more than a 1MB sequential `bs`. This resembles compile, library, and interactive EDA frontend tools.
* *EDA_BACKEND* — 50/50 sequential read/write of larger assembly-style files. Sequential 64K–1MB behavior dominates; this is the profile that benefits from larger NFS transfers, pNFS, and session trunking.
* *EDA_BLENDED* — both, with 3 frontend processes per 2 backend processes, so the wire mix includes small metadata I/O and large sequential I/O in the same run.
* Other SPECstorage 2020 workloads (SWBUILD, AI_IMAGE, GENOMICS, VDA) likewise mix small metadata with larger sequential transfers; VDA and AI_IMAGE are the more throughput-oriented profiles.

For synthetic isolation of one size, use xref:appendix-synthetic-benchmarks.adoc#synthetic-application-block-sizes[elbencho/fio block-size recipes] instead of editing SPEC workload YAML (editing YAML makes a run non-publishable). Typical application sizes (4K/8K databases, 64K SQL extents, 256K/1MB sequential NAS) are listed in xref:appendix-nfs-considerations.adoc#typical-benchmark-block-sizes[NFS: Typical sizes].

[[definition-of-relevant-operations-in-spec-sfs-2020]]
=== Definition of relevant operations in SPEC SFS 2020

The following section defines the operations mentioned in <<frontend-eda-workload-breakdown----specsfs-2020>> and <<backend-eda-workload-breakdown>>.

[cols="1,1",options="header"]
|===
| Operation type | What it does
| read | Sequential reads to an already open file.
| read file | Open, read, close file. End-to-end read.
| mmap read | Memory map read.
| random read | Random read (SPEC: rand read).
| write | Sequential write to an already open file.
| write file | Open, write, close. End-to-end write.
| mmap write | Memory map write.
| random write | Random write (SPEC: rand write).
| rmw | Read/modify/write.
| append | Add data to end of existing file.
| mkdir | Make directory.
| rmdir | Remove directory.
| readdir | List contents of directory. (Includes readdir+ operations)
| create | Create file metadata operation; checks if file exists, allocates a new inode.
| unlink | Deletes a file.
| unlink2 | 2nd unlink on a different file.
| stat | Retrieves the attributes of a file or directory, such as size, permissions, owner, and timestamps. (ie, du and ls)
| access | Checks the access permissions for a file or directory to determine if the client has the necessary permissions (read, write, execute).
| rename | Rename a file or folder.
| copyfile | Copies a file from one to another.
| lock | Locks a file (SPEC: locking).
| chmod | Change the permissions of a file or folder.
| statfs | Retrieve information about the overall file system. (ie, df)
| pathconf | Retrieves configuration information about a file or directory, such as maximum filename length, maximum path length, and other file system limits.
|===
