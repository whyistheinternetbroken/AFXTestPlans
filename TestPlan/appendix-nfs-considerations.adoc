[[nfs-considerations]]
== NFS considerations

For NFS workloads, NFSv3 can be used and generally will perform better with high metadata workloads (such as high file count workloads that create many files).
Most EDA workloads make use of NFSv3 -- especially EDA frontend workloads, which tend to be more metadata heavy.

[[what-is-nfs-session-trunking]]
=== What is NFS session trunking

NFSv4.1 session trunking (link:https://datatracker.ietf.org/doc/html/rfc5661#section-2.10.5[RFC 5661, section 2.10.5]) associates multiple TCP connections with a single NFSv4.1 session (one client ID, one session, multiple transports). The client spreads NFS operations across those connections (typically round-robin) to increase throughput and to keep I/O flowing if one path fails.

In ONTAP, session trunking is supported beginning with 9.14.1 (`-v4.1-trunking enabled`). A trunking group is a set of data LIFs on the *same node* of the same SVM. Trunks do not span nodes. LIFs in a trunking group should be on their home ports, and it is a best practice that they share the same failover group. ONTAP supports up to 16 trunked connections per node from a given client. Session trunks require at least two routable data interfaces per node; pNFS still requires at least one routable interface per node. All SVM data interfaces used for testing should be routable to the clients.

Clients discover trunk members in one of these ways:

* Automatically, using a mount option that causes the client to query `FS_LOCATIONS` (seen in packet captures as a GETATTR for `fs_location4`). RHEL uses `trunkdiscovery`. Ubuntu typically uses `max_connect=n`. On RHEL, `max_connect` is treated as nconnect and does *not* enable session trunking.
* Manually, by mounting each node-local LIF IP to the same export (and, on some Ubuntu releases, issuing a mount per interface).

When trunking is used with pNFS, each node can form its own session trunk. pNFS then localizes data paths across the cluster while trunking adds parallelism on each node.

For how to confirm trunking is active, see <<pnfs-and-session-trunking-validation>>. For official product behavior, see link:https://docs.netapp.com/us-en/ontap/nfs-trunking/index.html[Learn about ONTAP NFS trunking] and link:https://docs.netapp.com/us-en/ontap/pnfs/pnfs-use-cases-concept.html[pNFS use cases in ONTAP].

[[nconnect]]
[[what-is-nconnect]]
=== What is nconnect

`nconnect` is a Linux NFS mount option (kernel 5.3 and later; see link:https://man7.org/linux/man-pages/man5/nfs.5.html[nfs(5)]) that opens multiple TCP connections -- up to 16 -- to a *single* NFS server IP address. Without nconnect, a mount typically uses one TCP connection, which can become a throughput bottleneck on high-bandwidth NICs. The client multiplexes RPC traffic across the connections (Linux uses round-robin by default).

ONTAP supports nconnect beginning with 9.8. This test plan uses nconnect primarily with NFSv3. The first mount to a given server IP on a client sets the nconnect value for that IP; later mounts to the same IP inherit the first mount's setting even if they specify a different value.

nconnect can improve single-client throughput, but it multiplies TCP connections. With pNFS, `nconnect=N` can apply to each advertised data-server address (for example, nconnect=4 across 4 pNFS devices can mean up to 16 connections per mount). In large client farms that can exhaust per-node TCP connection limits (see Hardware Universe), prefer lower nconnect values or omit nconnect.

Verify nconnect by counting established connections to port 2049 (`netstat` or `ss`). See <<nconnect-recommendation>> for the test-plan recommendation.

[[comparing-nconnect-and-nfs-session-trunking]]
=== Comparing nconnect and NFS session trunking

Both features add parallelism by using more than one TCP connection. They do it differently:

[cols="1,2,2"]
|===
| | *nconnect* | *Session trunking*
| What it multiplies | Multiple TCP connections to *one* LIF/IP | Multiple TCP connections across *multiple* LIFs (multipathing)
| NFS versions | NFSv3 and NFSv4.1 (client-dependent) | NFSv4.1 and later only
| ONTAP | 9.8 and later | 9.14.1 and later (`-v4.1-trunking`)
| Typical mount option | `nconnect=8` (max 16) | RHEL: `trunkdiscovery`. Ubuntu: `max_connect=n`. Or mount each LIF IP.
| Network requirement | One data IP is enough; extra NIC queues or LACP can still help | At least two data LIFs per node, same home node, all routable
| Scale limit | 16 connections per mount endpoint | 16 trunked connections per node per client
| With pNFS | Connections can be created per pNFS data-server device | One session trunk per node; pNFS localizes data across nodes
|===

When using pNFS, use only session trunking *or* nconnect -- not both. Combining them can leave nconnect on the metadata server path while data servers use a single connection.

Use nconnect when you have a single endpoint (typical NFSv3 metadata-heavy tests) and want more concurrency without extra LIFs. Use session trunking when you have multiple LIFs per node and want NFSv4.1+ throughput plus path diversity; with pNFS that also gives a trunk per node across the cluster. If extra NICs and LIFs are available, trunking can exceed what nconnect can do on a single LIF.

For this test plan: NFSv3 -- `nconnect=8`; NFSv4.1 + pNFS -- session trunking (`trunkdiscovery` or `max_connect`), not nconnect.

[[recommended-mount-options-with-nfsv3]]
=== Recommended mount options with NFSv3


[source,console]
----
-o vers=3,tcp,hard,intr,nconnect=8
----


[[recommended-mount-options-for-nfsv41]]
=== Recommended mount options for NFSv4.1

For high read/write workloads -- such as those found with AI/ML training and inference, NFSv4.1 with parallel NFS and session trunking offer performance benefits that NFSv3 does not, with the following considerations:

* pNFS will require at least one routable network interface per node to function properly.
* With pNFS, avoid including non-routable network interfaces in the SVM configuration.
* NFS session trunking works best when there are routable network interfaces on multiple ports per node to provide added throughput possibilities.
* Session trunking and pNFS are supported only with NFSv4.1 and later.
* Session trunking is provided via a mount option. The method of enabling trunking for an NFS mount will depend on the Linux version in use.
* pNFS requires no special mount options.

[[ubuntu-22-and-later]]
==== Ubuntu 22 and later

AI/ML training and inference workloads with NFSv4.1

[source,console]
----
-o vers=4.1,tcp,hard,intr,nocto,actimeo=3600,max_connect=8
----


*Note:* A mount command will need to be issued for each individual network interface to ensure session trunking is in use with Ubuntu.

Rather than relying on individual mount commands, use the /etc/fstab file to configure the mount commands and then run them all at once with mount -a. See <<using-fstab,using fstab>>.

[[rhel-9x-and-later]]
==== RHEL 9.x and later

AI/ML training and inference workloads with NFSv4.1

[source,console]
----
-o vers=4.1,tcp,hard,intr,nocto,actimeo=3600,trunkdiscovery
----


*Note:* Trunkdiscovery mount option will automatically find the network paths that are a part of the trunking group.

[[client-tuning-considerations]]
=== Client tuning considerations

Client tuning should be changed one variable at a time and validated against the target workload. The recommendations below are starting points for benchmark tests, not universal production settings. For client hardware, NIC, and operating-system prerequisites, see xref:setup.adoc#clients[Setup: Clients].

[[wsize-and-rsize]]
==== Wsize and rsize

The NFS `rsize` and `wsize` mount options set the maximum read and write transfer sizes for a mount. ONTAP enforces the upper limit configured by `-tcp-max-xfer-size`; clients can negotiate that value or request a smaller value, but cannot exceed the server maximum.

[[wsize-rsize-recommendation]]
===== Recommendation

Start with 256K (`rsize=262144,wsize=262144`) and then test 1MB (`rsize=1048576,wsize=1048576`) to find the best fit. Larger transfers can reduce the RPC count and protocol overhead for throughput workloads. Smaller transfers can reduce per-operation latency for latency-sensitive workloads.

[[small-window-sizes]]
===== Small transfer sizes

When the mount transfer size is smaller than the application I/O size, the client must split one application request into multiple NFS operations. For example, a 64K application request over an 8K mount transfer size requires eight NFS operations, increasing operation count and CPU/network overhead.

[[large-window-sizes]]
===== Large transfer sizes

A larger transfer size can combine application blocks into fewer NFS operations. This often benefits sequential reads and writes, but larger requests can take longer to complete. If latency is more important than aggregate throughput, test a transfer size closer to the application's I/O size.

[[other-considerations]]
===== Other transfer-size considerations

Random application I/O is often smaller than the configured maximum and is not forced to use the full `rsize` or `wsize`. Buffered sequential I/O is more likely to approach the negotiated maximum. Direct-I/O benchmark generators remain bounded by the mount maximum but may issue smaller application requests.

[[application-block-sizes]]
===== Application block sizes and how they interact with storage

The *application I/O size* (fio/elbencho `bs`, database page, hypervisor grain) is not the same as the *NFS transfer size* (`rsize`/`wsize`) or the *ONTAP* `-tcp-max-xfer-size`. Storage sees NFS operations after the client has split or coalesced the application request:

* If application I/O is larger than the mount transfer size, the client issues multiple NFS operations. Internal NFSv4.1 characterization used a 1MB tool block size on a 256K mount and observed four NFS operations on the wire per client request.
* If application I/O is smaller than the mount maximum, each request is typically one NFS operation at the application size. Raising `rsize`/`wsize` does not enlarge 4K or 8K random I/O.
* Direct I/O follows the generator's `bs` up to the mount maximum. Buffered sequential I/O is more likely to fill `rsize`/`wsize` because of page cache and readahead.

ONTAP performance characterization commonly reports a "four corners" set: 8K random IOPS, 64K sequential, and 1MB sequential throughput. Historically many lab runs centered on 8K random and 64K sequential; more recent customer and AI/EDA deployments also use 32K–256K random and 64K–1MB sequential. See <<typical-benchmark-block-sizes>> for application examples and xref:test-08-customer-workload-benchmarks.adoc#application-block-sizes-for-benchmarks[Test 8] for how to pick a size for a run.

[[typical-benchmark-block-sizes]]
====== Typical sizes used in this test plan

[cols="1,2,3"]
|===
| Size | Why it is used in benchmarks | Example applications
| 4K | Matches Linux memory pages, common SSD/NVMe logical blocks, and many guest file systems. Stresses IOPS and latency rather than bandwidth. | Virtual-machine guest file systems; VMDK-aligned random I/O; general OS paging
| 8K | Standard random "corner" for ONTAP and Fusion-style random workloads. Matches common database pages. | Oracle and PostgreSQL 8K pages; SQL Server 8K pages; OLTP-style random read/write
| 16K | Mid-size random I/O between database pages and sequential transfers. | MySQL/InnoDB default 16K pages
| 32K–64K | Sequential and mixed-I/O corner. 64K is the ONTAP NFS default `-tcp-max-xfer-size` and a common EDA sequential size. | SQL Server 64K extents / recommended NTFS allocation unit; EDA sequential and mixed tests; VMware NFS historically negotiated 64K `rsize`/`wsize`
| 256K | Starting NFS mount transfer size in this plan; large enough to cut RPC count without always using the 1MB maximum. | TensorFlow TFRecord default reader size (~256K); sequential throughput characterization; Azure NetApp Files Linux sequential benchmarks
| 1MB | ONTAP NFS maximum transfer size; used for high-throughput sequential reads/writes and large AI files. | AI/ML training ingest and checkpoint bursts; media/VDA sequential streams; AFX 1MB sequential characterization
|===

[[close-to-open-consistency-and-cache-attribute-timers]]
==== Close-to-open consistency and attribute caching

NFS clients cache data and attributes to avoid a server request for every application access. Close-to-open consistency (`cto`, the default) revalidates a file when it is opened. Attribute timers (`acregmin`, `acregmax`, `acdirmin`, and `acdirmax`) control how long file and directory attributes can remain cached.

[[cto-recommendation]]
===== Recommendation

Use default `cto` behavior for shared read/write datasets where clients must observe changes promptly. Consider `nocto` with a longer `actimeo` only for read-only or read-mostly datasets whose update workflow can tolerate stale attributes. For read-heavy EDA libraries, `nocto,actimeo=600` is a useful test point; do not apply it blindly to multi-writer workloads.

[[how-attribute-cache-timers-work]]
===== How attribute cache timers work

The client begins with the minimum timer and increases the trusted interval toward the maximum while attributes remain valid. `actimeo=N` sets all four attribute-cache timers to the same value. A larger value reduces GETATTR traffic but increases the period during which metadata can be stale.

[[close-to-open-cto-consistency]]
===== Close-to-open (`cto`) consistency

With `cto`, opening a file triggers validation against the server so the application receives the server's current contents. Directory-entry visibility is still influenced by directory attribute-cache timers. Use `cto` for shared home directories, collaborative build trees, and mixed read/write/metadata workloads.

[[no-close-to-open-nocto-consistency]]
===== No close-to-open (`nocto`) consistency

With `nocto`, the client trusts its cached view until the attribute timers expire. This can substantially reduce metadata traffic for static datasets, but newly created or removed files and recent content changes might not be visible immediately. Avoid it when multiple clients concurrently modify shared files.

[[nconnect-recommendation]]
==== Nconnect recommendation

For NFSv3 benchmark workloads, begin with `nconnect=8` and compare against 1, 4, and 16 connections. For NFSv4.1 with pNFS, use session trunking instead of combining nconnect and trunking.

[[nfs-readahead]]
==== NFS readahead

NFS readahead requests sequential file blocks before the application asks for them. Older Linux releases commonly set readahead to 15 times the mount's `rsize`; RHEL 8.3+ and Ubuntu 18.04+ commonly default to 128 KiB regardless of `rsize`, which can constrain sequential-read throughput.

[cols="1,1"]
|===
| Rsize | 15x readahead
| 64 KiB | 960 KiB
| 256 KiB | 3,840 KiB
| 1 MiB | 15,360 KiB
|===

[[readahead-recommendation]]
===== Recommendation

For sequential-read tests, compare the client default with readahead set to 15 times `rsize`. For random or latency-sensitive tests, retain the default unless measurements show a benefit.

[[managing-readahead-values-on-clients]]
===== Managing readahead values on clients

Readahead is associated with the backing-device (`bdi`) entry for an NFS mount. The following commands identify the entry and view or set the value in KiB:

[source,console]
----
MOUNT=/mnt/afx
BDEV=$(awk -v m="$MOUNT" '$5 == m {print $3}' /proc/self/mountinfo)
cat "/sys/class/bdi/$BDEV/read_ahead_kb"
echo 3840 | sudo tee "/sys/class/bdi/$BDEV/read_ahead_kb"
----

[[viewing-readahead-values-on-clients]]
===== Viewing readahead values on clients

Use `/proc/self/mountinfo` instead of assuming a block-device name:

[source,console]
----
awk -v m="/mnt/afx" '$5 == m {print $3}' /proc/self/mountinfo
----

[[readahead-view-example]]
Example output:

[source,console]
----
0:30
----

Session trunking can expose multiple backing-device entries for the same path. Apply and verify the setting for every entry returned.

[[manually-setting-readahead]]
===== Manually setting readahead

Writing `read_ahead_kb` changes the active mount dynamically but does not survive an unmount or reboot:

[source,console]
----
echo 15360 | sudo tee /sys/class/bdi/0:30/read_ahead_kb
----

[[persistently-setting-readahead]]
===== Persistently setting readahead for NFS mounts

Persist readahead with a tested `udev` rule or a client startup/mount script. Because backing-device identifiers can change, use a rule that checks `/proc/fs/nfsfs/volumes` rather than hard-coding `0:N`. See link:https://learn.microsoft.com/en-us/azure/azure-netapp-files/performance-linux-nfs-read-ahead[Linux NFS read-ahead best practices] for an example.


[[using-fstab]]
=== Using fstab

The /etc/fstab file on Linux clients can be used to set NFS mount points in a single file to simplify mount operations. Below is an example of an entry in /etc/fstab for an NFS mount:

[source,console]
----
SVM:/NFS_export     /mnt/NFS_export nfs     intr,nfsvers=4.1,max_connect=8,tcp   0 0
----

When an NFS mount is needed and fstab is populated, the command can be:

[source,console]
----
# mount -a
----


[[using-automounter]]
=== Using automounter

The automounter is a service that can be used to configure NFS mount points and have the autofs process manage mounts when a directory is accessed without needing interaction from end users to issue mount commands.
Automounter requires:
* Autofs installed
* /etc/auto.master configured
* /etc/auto.[map] configured (ie, auto.misc)
Below are some examples of auto.master and auto.misc file configurations.
*/etc/auto.*master

[source,console]
----
/- /etc/auto.misc
----

*/etc/auto.misc*

[source,console]
----
/mnt/NFS_export -rw,nosuid,hard,tcp,max_connect=8 10.192.160.180:/NFS_export
/mnt/NFS_export -rw,nosuid,hard,tcp,max_connect=8 10.192.160.181:/NFS_export
/mnt/NFS_export -rw,nosuid,hard,tcp,max_connect=8 10.192.160.182:/NFS_export
/mnt/NFS_export -rw,nosuid,hard,tcp,max_connect=8 10.192.160.183:/NFS_export
----


[[nfs-64-bit-file-ids]]
=== NFS 64-bit file IDs

FlexGroup volumes allow up to 400 billion files, provided 64-bit file IDs are enabled. While these should be enabled as part of the initial setup and configuration, ensure they are enabled in the environment during xref:test-01-validate-cluster-setup.adoc[Test 1: Validate cluster setup].
To enable them:

[source,console]
----
AFX::> set advanced; nfs modify -v3-64bit-identifiers enabled -v4-64bit-identifiers enabled
----


[[pnfs-and-session-trunking-validation]]
=== pNFS and session trunking validation

When using pNFS and/or session trunking, it can be difficult to determine if the protocol features are actively being used. ONTAP provides commands to check these features for activity.
*To show pNFS devices*

[source,console]
----
AFX::> set advanced -confirmations off
AFX::*> pnfs devices show -vserver svm1
AFX::*> pnfs devices mappings show -vserver svm1
----

*To show connected NFS clients*

[source,console]
----
AFX::> nfs connected-clients show -vserver svm1
AFX::> network connections active show -service nfs
----

*pNFS and NFSv4.1 session trunking calls validation*

[[pnfs-and-nfsv41-session-trunking-calls-validation]]
To validate if pNFS and/or session trunking are active, use the following commands to look for incrementing values for pNFS/trunking counters.

*Note:* For a list of pNFS and session trunking specific counters (and examples) see xref:appendix-statistics-counters.adoc#statistics-counters[Statistics Counters].


[source,console]
----
AFX::> set diag
AFX::*> nfs show -fields v4.1,v4.1-pnfs,v4.1-trunking
AFX::*> statistics start -object nfsv4_1|nfsv4_1_diag -sample-id AFX
AFX::*> statistics show -object nfsv4_1|nfsv4_1_diag -counter [name1]|[name2]|[name3] -sample-id AFX
----

To clear pNFS devices (when adding or removing interfaces):

[source,console]
----
AFX::> set diag -c off
AFX::*> pnfs lif-mapping-cache flush -node *
AFX::*> pnfs devices cache flush -node * -vserver [SVM1]
AFX::*> pnfs devices invalidate -global-device-table-id *
----
