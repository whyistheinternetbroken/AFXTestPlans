[[performance-testing-considerations]]
== Performance testing considerations

Performance testing is generally intended to find the edges of what a system can achieve in specific workload scenarios. Most of the time, the ONTAP default settings do not need to be adjusted to see good performance for most workloads, but in some cases, you may want to adjust some configurations to optimize the system. This section covers some general considerations and configuration guidelines rather than serving as an actual test.

[[nfs-export-policy-configuration]]
== NFS export policy configuration

Export policies in ONTAP are how access to NFS exports are controlled. Every volume requires an export policy to be set, with rules configured in the policy. If no rules are configured in a policy, that will be considered as "no access."
For performance benchmarking, we are likely less concerned with permissions to the clients being used for testing and instead would like to avoid any permission-related errors.
As a result, it is recommended to ensure that any export policy rule is set to wide-open access for the data volume, but only to the clients being used to access datasets. In addition, the vsroot policy *must* allow read access in the policy for path traversal.

*vsroot policy (uses "default" policy)*

[source,console]
----
export-policy rule create -policyname default -clientmatch 0/0 -rorule any -rwrule never
----

*data volume policy*

[source,console]
----
export-policy create -policyname [name] -vserver [SVM]
export-policy rule create -policyname [name] -clientmatch [client1],[client2],..[clientN] -rorule any -rwrule any -superuser any -anon 0 -chown-mode unrestricted -ntfs-unix-security-ops ignore
----

*Note:* The NFS server configuration reference table and benchmark CLI command are consolidated in xref:setup.adoc#nfs-server-configuration[Setup: NFS Server Configuration].

[[special-considerations----flexgroup-volumes]]
=== Special considerations -- FlexGroup volumes

If the workload creates many large files (>1GB) in a single folder, modify the volume's workflow to data:

[source,console]
----
AFX::> set advanced; vol modify -vserver [SVM] -volume [FlexGroup name] -workflow data
----

Changing this setting from the default is not recommended for production workloads unless directed by support. Due to the nature of benchmark tools, changing this option enforces a round robin placement of files and file parts across constituent volumes to ensure even distribution of data (at the potential cost of latency for remote placement).

If the workload is VMware datastores hosted on a FlexGroup volume, disable the -gdd option:

[source,console]
----
AFX::> set diag; vol modify -vserver [SVM] -volume [FlexGroup name] -granular-data disabled
----

[[why-snapshots-are-disabled]]
=== Why snapshots are disabled

In general, snapshots in ONTAP are not detrimental to overall system performance. However, in benchmarking, we would disable snapshots for two reasons:

* Granular control over the environment -- We can create snapshots when we want to create them to better control the scenarios when snapshots are created and make it easier to measure their impact.
* Data churn -- Many benchmark tests will create a lot of data and then subsequently overwrite or delete that data, which will rapidly grow the size of any existing snapshots on the volume. To avoid space allocation issues, we disable the snapshot *policy*. A single manual snapshot of the *empty* volume is useful as a restore point so you can return the volume to empty without client-side deletes; see xref:test-08-customer-workload-benchmarks.adoc#overwrites-and-deletes[Test 8: Overwrites and deletes]. If clients still delete or overwrite files while that snapshot exists, the snapshot grows — watch capacity. Overwrite and delete also change the write path versus a first fill; isolate those phases as described in the same Test 8 section.

*Note:* Snapdir access is also disabled to prevent unwanted filesystem crawls across snapshots.

[[mount-options]]
== Mount options

Mount options vary by protocol, client release, and workload. The canonical NFSv3/NFSv4.1 selection guidance is in xref:appendix-nfs-considerations.adoc[NFS Considerations]; copy-ready mount commands are in xref:benchmark-configuration-reference.adoc#nfs-mount-commands[NFS mount commands].

Base options (applies to all clients/scenarios):

[source,console]
----
-o tcp,hard,intr
----

*Session trunking (OS-specific)*

[source,console]
----
RHEL: trunkdiscovery
Ubuntu (depends on version): trunkdiscovery (newer releases)
                             max_connect=4 (older releases)
----

[[nfs-wsize-and-rsize]]
=== NFS wsize and rsize

Transfer size affects RPC count, throughput, and latency. Begin with 256K and compare against 1MB rather than assuming the largest value is always best. See xref:appendix-nfs-considerations.adoc#wsize-and-rsize[Wsize and rsize].

*RDMA specific options*

[source,console]
----
rdma,write=eager
----

*Other mount options*

Some workloads might benefit from special mount options during benchmark tests. The following table shows some of those options and what use cases might see performance improvements.

*Alternate NFS mount options and their use cases*

[cols="1,1,1"]
|===
| *NFS mount option* | *Description* | *Use case*
| `nocto` | Disables "close-to-open" cache consistency. The client will not revalidate cached file attributes when a file is opened, relying instead on cached data even if it may be stale. | Read-heavy, single-client workloads where files rarely change (e.g., static web content, software libraries, read-only media archives). Not suitable for multi-client writes.
| `cto` | Enables close-to-open cache consistency (default). When a file is opened, the client checks with the server to ensure its cached copy is still valid. Guarantees that a file closed on one client is seen as up-to-date when opened on another. | Multi-client shared access workloads where data consistency matters (e.g., shared home directories, collaborative development environments).
| `actimeo` | Sets all attribute cache timeouts (acregmin, acregmax, acdirmin, acdirmax) to a single value in seconds. Controls how long the client trusts cached file/directory metadata before revalidating with the server. | Simplifying tuning when you want a uniform caching policy. High values benefit read-heavy/static workloads; low values (e.g., actimeo=0) suit rapidly changing data needing near-real-time consistency.
| `acregmin` | Sets the minimum time (seconds) the client caches attributes for a regular file before revalidating. Default is typically 3s. | Workloads with frequently updated small files where you want to fine-tune freshness vs. performance (e.g., log ingestion, config file polling).
| `acregmax` | Sets the maximum time (seconds) the client caches attributes for a regular file. Default is typically 60s. | Mostly-static file workloads where extending the max reduces metadata chatter (e.g., large read-only datasets, package repositories).
| `acdirmin` | Sets the minimum time (seconds) the client caches attributes for a directory before revalidating. Default is typically 30s. | Workloads with frequent directory listing or creation (e.g., build systems, mail spools with Maildir format) where directory freshness matters.
| `acdirmax` | Sets the maximum time (seconds) the client caches attributes for a directory. Default is typically 60s. | Stable directory structures that rarely change — raising this reduces GETATTR calls (e.g., large static directory trees, archival storage).
| `clientaddr` | Specifies the client IP address to advertise to the NFS server for callback communication (NFSv4/v4.1+). The server uses this address to send delegation recalls and other callbacks. | Multi-homed clients or environments with complex networking (e.g., clients with multiple NICs, VPN/overlay networks, or NAT) where the auto-detected address may be incorrect.
| `nconnect` | Creates multiple TCP connections to one LIF/IP. | NFSv3 tests that need more concurrency than one TCP flow. Do not combine it with session trunking when using pNFS; see xref:appendix-nfs-considerations.adoc#comparing-nconnect-and-nfs-session-trunking[the comparison].
| `krb5,krb5i,krb5p` | Specifies what Kerberos security flavor to use with the mount. Requires Kerberos configuration to work properly. See link:https://www.netapp.com/media/19384-tr-4616.pdf[TR-4616: NFS Kerberos in ONTAP with Active Directory] for details. | Securing NFS mounts; has a negative impact on performance.
|===

[[client-configuration]]
== Client configuration

The client configuration used for our internal benchmarking is covered in xref:setup.adoc#clients[Setup: Clients]. The following contains some additional configuration considerations. This list is not considered exhaustive and will be modified over time to accommodate additional use cases/scenarios.

=== NFS readahead

Modern RHEL and Ubuntu clients commonly default to 128 KiB readahead, which can constrain sequential reads. Compare that default with 15 times the mount `rsize`; see xref:appendix-nfs-considerations.adoc#nfs-readahead[NFS readahead].

[[network-configuration]]
== Network configuration

The following section covers some general networking guidance for client and storage networking. These are based on the internal benchmark tests we have done.

[[storage-network-considerations]]
=== Storage network considerations

* At least one data IP address per node, per SVM (more per node is better)
* Maximum of 16 IP addresses per node, per SVM
* All data interfaces routable to all clients
* Bonded/teamed ports per node using LACP
* MTU size of 9000 (end to end)
* Priority flow control (PFC priority 3) enabled when using RDMA
* DNS round robin/load balancing configured to include all data interface IP addresses

[[client-network-considerations]]
=== Client network considerations

* Dual NICs bonded for RoCE (LACP)
* RX/TX ring buffers set to 8192
* PFC and DSCP configured per NIC (when using RDMA)
* RoCE traffic class set using cma_roce_tos (when using RDMA)
* sunrpc.rdma_slot_table_entries set to 200

[[disable-storage-efficiencies]]
=== Disable storage efficiencies

In general, storage efficiencies are one of the selling points for a production workload, as they can generate large space savings across a variety of workloads. However, in performance benchmarking, they offer less value (as many simulated workloads are either uncompressible or are zero-byte workloads and always deduplicating). As a result, we recommend disabling all storage efficiencies while performing benchmark tests.

The copy-ready commands and restoration warning are in xref:benchmark-configuration-reference.adoc#ontap-storage-efficiency-commands[Storage efficiency].

=== Aggressive readahead

Aggressive readahead can help improve read performance for specific workloads (such as sequentially named files). For feature configuration, caveats, and statistics are covered in xref:feature-aggressive-readahead.adoc[Aggressive Readahead Feature Test].
