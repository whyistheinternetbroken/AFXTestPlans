== Customer workload testing -- Performance benchmarks

In lieu of - or in addition to -- testing real data workloads, storage benchmark tests can also be run against the NetApp AFX cluster to display some of the potential performance.
For EDA workloads, we can leverage link:https://www.spec.org/storage2020/[SPEC SFS 2020 / SPECstorage Solution 2020 EDA] for benchmarking. This benchmark can also be used for general testing of small random IO (including high metadata) and larger sequential IO.

For AI/ML workloads, we will leverage link:https://mlcommons.org/benchmarks/storage/[MLPerf Storage (MLCommons)], which can also act as a throughput-specific benchmark.

For synthetic throughput, IOPS, metadata, or shared-file tests, use xref:appendix-synthetic-benchmarks.adoc[Synthetic Benchmarks].

*Note:* Review xref:test-07-08-performance-testing-considerations.adoc[Performance testing considerations] for rationale and xref:benchmark-configuration-reference.adoc[Benchmark Configuration Reference] for copy-ready setup and monitoring commands.

[[application-block-sizes-for-benchmarks]]
=== Application block sizes and storage

Match the *application I/O size* to the question you are asking. Storage sees NFS operations after the client applies `rsize`/`wsize`. A 1MB application write on a 256K mount becomes four NFS writes; an 8K random read on a 1MB mount remains one 8K NFS read. Details are in xref:appendix-nfs-considerations.adoc#application-block-sizes[NFS: Application block sizes].

ONTAP characterization typically reports 8K random, 64K sequential, and 1MB sequential ("four corners"). Use 4K/8K when the goal is IOPS or database/VM-like latency; use 64K/256K/1MB when the goal is sequential throughput.

[cols="1,2,3"]
|===
| Size | Typical benchmark use | Example applications
| 4K | Random IOPS and latency | Guest file systems, OS paging, VMDK-aligned random I/O
| 8K | Default random corner | Oracle, PostgreSQL, and SQL Server 8K pages; OLTP
| 16K | Database random I/O | MySQL/InnoDB 16K pages
| 32K–64K | Sequential/mixed corner; EDA sequential | SQL Server 64K extents; EDA sequential; VMware NFS 64K transfers
| 256K | First NFS mount size in this plan; sequential throughput | TensorFlow TFRecord reads; mixed sequential NAS
| 1MB | Maximum NFS transfer; AI/media throughput | Training ingest, checkpoints, VDA/media streams
|===

Pick the generator `bs` (or accept SPEC/MLCommons built-in sizes) first, then set the mount so it does not silently split that I/O. Start mounts at 256K and compare 1MB for throughput tests. Keep the mount at or above the application size for sequential work; do not expect a 1MB mount to change 4K/8K random results.

[cols="<1",width="100%"]
|===
a| *Test procedure:*

. Select the benchmark that best represents the objective:
** SPEC SFS for standardized EDA, software-build, AI-image, genomics, or VDA workload curves.
** MLCommons for AI training ingest, checkpointing, vector database, or optional KV-cache behavior.
** elbencho, mdtest, or fio for controlled synthetic throughput, IOPS, metadata, and shared-file experiments.
. Size and create a dedicated benchmark FlexGroup by using xref:benchmark-configuration-reference.adoc#ontap-volume-commands[Benchmark FlexGroup volume]. Review xref:datasets-workloads.adoc#ontap-limits-considerations[ONTAP limits] and ensure capacity and inode headroom for the largest planned dataset.
. Configure exports, ONTAP NFS options, clients, and mounts with xref:benchmark-configuration-reference.adoc[Benchmark Configuration Reference].
. Validate protocol, transfer size, pNFS/trunking or nconnect, client paths, free space, and write access before generating data.
. Follow the selected execution guide: xref:appendix-spec-sfs.adoc[SPEC SFS], xref:appendix-mlcommons.adoc[MLCommons], or xref:appendix-synthetic-benchmarks.adoc[Synthetic Benchmarks].
. Start with 1–2 concurrent jobs per client (SPEC: 1 JOB per load generator; MLCommons: 2 accelerators or datagen processes; elbencho/fio: `-t`/`numjobs=2`; mdtest: 1 rank per client). Ramp jobs and client count independently through 1, 2, 4, 8, then 16. Stop when aggregate throughput/IOPS plateaus, latency rises materially, or a client saturates. See the concurrency sections in each guide for workload-specific starting points.
. Run a smoke test, then ramp load while monitoring clients and ONTAP. Change one variable at a time and repeat each final point.
. Capture results and configuration metadata. Use xref:test-09-performance-monitoring.adoc[Test 9] for dashboards and xref:benchmark-configuration-reference.adoc#statistics-capture-commands[Statistics capture] for CLI samples.

a| *Expected outcome(s):*

* Dataset generation and benchmark initialization complete without mount, capacity, inode, or client-resource errors.
* Every measured point produces a result set and matching ONTAP statistics sample with the configuration metadata needed for repeatable comparisons.
* Exploratory results are labeled separately from rules-compliant SPEC or MLCommons results.
|===
