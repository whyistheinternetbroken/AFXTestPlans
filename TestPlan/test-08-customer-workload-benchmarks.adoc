[[customer-workload-testing--performance-benchmarks]]
== Customer workload testing -- Performance benchmarks

In lieu of - or in addition to -- testing real data workloads, storage benchmark tests can also be run against the NetApp AFX cluster to display some of the potential performance.
For EDA workloads, we can leverage link:https://www.spec.org/storage2020/[SPEC SFS 2020 / SPECstorage Solution 2020 EDA] for benchmarking. This benchmark can also be used for general testing of small random IO (including high metadata) and larger sequential IO.

For AI/ML workloads, we will leverage link:https://mlcommons.org/benchmarks/storage/[MLPerf Storage (MLCommons)], which can also act as a throughput-specific benchmark.

For synthetic throughput, IOPS, metadata, or shared-file tests, use xref:appendix-synthetic-benchmarks.adoc[Synthetic Benchmarks].

*Note:* Review xref:general-guidance.adoc[General guidance] for a short checklist, xref:test-07-08-performance-testing-considerations.adoc[Performance testing considerations] for rationale, and xref:benchmark-configuration-reference.adoc[Benchmark Configuration Reference] for copy-ready setup and monitoring commands.

[[application-block-sizes-for-benchmarks]]
=== Application block sizes and storage

Match the *application I/O size* to the question you are asking. Storage sees NFS operations after the client applies `rsize`/`wsize`. A 1MB application write on a 256K mount becomes four NFS writes; an 8K random read on a 1MB mount remains one 8K NFS read. Details are in xref:appendix-nfs-considerations.adoc#application-block-sizes[NFS: Application block sizes].

ONTAP characterization typically reports 8K random, 64K sequential, and 1MB sequential ("four corners"). Use 4K/8K when the goal is IOPS or database/VM-like latency; use 64K/256K/1MB when the goal is sequential throughput.

[cols="1,2,3"]
|===
| Size | Typical benchmark use | Example applications
| 4K | Random IOPS and latency | Guest file systems, OS paging, VMDK-aligned random I/O
| 8K | Default random corner | Oracle, PostgreSQL, and SQL Server 8K pages; OLTP
| 16K | Database random I/O | MySQL/InnoDB 16K pages
| 32K–64K | Sequential/mixed corner; EDA sequential | SQL Server 64K extents; EDA sequential; VMware NFS 64K transfers
| 256K | First NFS mount size in this plan; sequential throughput | TensorFlow TFRecord reads; mixed sequential NAS
| 1MB | Maximum NFS transfer; AI/media throughput | Training ingest, checkpoints, VDA/media streams
| >1MB (for example 4–16MB) | Application request size only; NFS still splits at 1MB | HPC MPI-IO, some media frames, large scientific/checkpoint buffers — see <<block-sizes-over-1mb>>
|===

Pick the generator `bs` (or accept SPEC/MLCommons built-in sizes) first, then set the mount so it does not silently split that I/O. Start mounts at 256K and compare 1MB for throughput tests. Keep the mount at or above the application size for sequential work; do not expect a 1MB mount to change 4K/8K random results.

[[block-sizes-over-1mb]]
==== Application I/O larger than 1MB

ONTAP NFS and Linux `rsize`/`wsize` stop at **1MB** (`-tcp-max-xfer-size` / mount maximum). Nothing in this plan can issue a 16MB NFS READ or WRITE. A generator `bs` of 4MB or 16MB is still 4 or 16 NFS operations of 1MB on a 1MB mount (more if the mount is 256K). Tool-reported IOPS and latency then describe the *application* request, not a single RPC.

Some applications *do* issue I/O larger than 1MB: HPC MPI-IO and similar codes often use 4–16MB transfers; uncompressed media/VDA frames and some capture pipelines are several MB per frame; scientific HDF5/NetCDF hyperslabs and some AI checkpoint writers use multi-MB buffers. Large *files* or *samples* (for example a ~146 MB U-Net3D file or a ~2.8 MB CosmoFlow sample) are sequential streams of many NFS operations, not one giant RPC. Hadoop/Spark-style 128MB *blocks* are layout units; client packet and read sizes are typically much smaller.

A 16MB `bs` is **not** a standard throughput corner for this plan. Use 1MB sequential when the question is NFS/ONTAP bandwidth. Use 4–16MB only when a customer application actually issues that request size, and label it as application I/O:

* GB/s often matches a well-tuned 1MB sequential run once the pipe is full (diminishing returns).
* Application latency is roughly the sum of the split RPCs, so it looks much worse than 1MB latency at the same concurrency.
* Application IOPS fall in proportion to `bs`. Outstanding bytes (`iodepth` × `bs`) grow quickly and can saturate client memory or queues with few jobs.
* Report ONTAP NFS size histograms and protocol IOPS alongside the tool numbers so a 16MB fio I/O is not compared to a 1MB four-corners result.

Details: xref:appendix-nfs-considerations.adoc#block-sizes-over-1mb[NFS: Sizes larger than 1MB].

[[overwrites-and-deletes]]
==== Overwrites and deletes during benchmark tests

First-write, overwrite, and delete are different storage paths. Treat them as separate measurements unless the application really mixes them.

* *First write (append / fill).* Creating new files or appending into empty files allocates new blocks. This is the usual peak sequential-write corner.
* *Overwrite.* Writing over existing data also frees the old blocks. Sequential overwrite throughput is typically lower and write latency higher than a first-write of the same size and concurrency. Random writes to a pre-created file set are overwrites. Do not fold a fill and an overwrite into one unlabeled "sequential write" interval.
* *Delete.* Unlink/remove walks file metadata and frees blocks in the background. Concurrent deletes can reduce write throughput and raise write latency (delete interference). Measure peak write with the dataset retained; measure delete rate on its own; combine them only when that mix is the question (EDA scratch/frontend, rotating checkpoints). For cleanup between runs, prefer a *baseline snapshot on the empty volume* before testing, then restore that snapshot afterward instead of deleting files and folders from clients. Restore avoids the cost of walking and unlinking the tree. Keep `snapshot-policy none` so only this manual snapshot exists. Client-side deletions and overwrites still cause that baseline snapshot to grow, so watch volume capacity and snapshot used space.

How to run it:

. Pre-create the dataset for overwrite and random-write tests. Keep the same files across overwrite comparisons.
. After a fill, start the overwrite iteration as a new measured phase. Do not average fill and overwrite together.
. Do not enable elbencho file/directory delete (`-F`/`-D`), mdtest unlink, or `rm` in the same window as a peak write unless you are testing interference. Cleanup belongs after the measured run. Prefer restoring an empty-volume baseline snapshot rather than unlinking the dataset from clients.
. Wait until reclaim finishes, or switch to a fresh directory/volume, before the next fill. Snapshot policy is `none` on the benchmark FlexGroup so scheduled snapshots do not capture churn; a single empty-volume baseline snapshot is the exception for restore-based cleanup. That snapshot still grows if clients delete or overwrite data — monitor capacity. See xref:test-07-08-performance-testing-considerations.adoc#why-snapshots-are-disabled[Why snapshots are disabled].
. SPEC SFS EDA_FRONTEND and similar mixed workloads already include create, overwrite, and unlink. Report those as application curves, not as four-corners sequential write.

Synthetic recipes: xref:appendix-synthetic-benchmarks.adoc#synthetic-overwrites-and-deletes[Synthetic: Overwrites and deletes]. Latency effects: xref:appendix-nfs-considerations.adoc#latency-tweaks[How benchmark tweaks affect latency].

Throughput (bytes/s) ≈ IOPS × I/O size. Use 4K/8K when you care about IOPS and per-op latency; use 256K/1MB when you care about GB/s. Average latency rises with concurrency; stop a ramp when p99 or average latency climbs materially and throughput flattens. How jobs, `nconnect`/trunking, direct I/O, readahead, and other knobs move latency is in xref:appendix-nfs-considerations.adoc#throughput-iops-latency[Throughput, IOPS, and latency] and xref:appendix-nfs-considerations.adoc#latency-tweaks[How benchmark tweaks affect latency].

a| *Test procedure:*

. Select the benchmark that best represents the objective:
** SPEC SFS for standardized EDA, software-build, AI-image, genomics, or VDA workload curves.
** MLCommons for AI training ingest, checkpointing, vector database, or optional KV-cache behavior.
** elbencho, mdtest, or fio for controlled synthetic throughput, IOPS, metadata, and shared-file experiments.

. Configure exports, ONTAP NFS options, clients, and mounts with xref:benchmark-configuration-reference.adoc[Benchmark Configuration Reference].
. Validate protocol, transfer size, pNFS/trunking or nconnect, client paths, free space, and write access before generating data.
. Follow the selected execution guide: xref:appendix-spec-sfs.adoc[SPEC SFS], xref:appendix-mlcommons.adoc[MLCommons], or xref:appendix-synthetic-benchmarks.adoc[Synthetic Benchmarks].
. Start with 1–2 concurrent jobs per client (SPEC: 1 JOB per load generator; MLCommons: 2 accelerators or datagen processes; elbencho/fio: `-t`/`numjobs=2`; mdtest: 1 rank per client). . Run a smoke test, then ramp load while monitoring clients and ONTAP. Change one variable at a time and repeat each final point.
. Capture results and configuration metadata. Use xref:test-09-performance-monitoring.adoc[Test 9] for dashboards and xref:benchmark-configuration-reference.adoc#statistics-capture-commands[Statistics capture] for CLI samples.
